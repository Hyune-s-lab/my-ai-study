# 모의면접 — 타임아웃 (Timeout)

> 면접관이 타임아웃으로 보려는 것은 **용어 암기가 아니라**: 장애가 어떻게 **전파(cascading failure)**되는지, **자원(스레드·커넥션)**이 어떻게 고갈되는지, 분산 환경에서 **타임아웃을 어떻게 설계**하는지에 대한 사고력이다.
> 형식: **Q(질문) → 모범답안 → 꼬리질문 → 감점 포인트(이렇게 답하면 약하다)**.

---

## 레벨 1 — 개념

### Q1. 타임아웃의 종류를 설명해보세요.

> 이 문서는 **API 게이트웨이(호출자 ↔ OpenAI 중계)** 를 만드는 서버 개발자 관점으로 작성한다.

**모범답안**: 게이트웨이는 **"서버이자 클라이언트", 두 얼굴**을 동시에 가진다. 같은 타임아웃 개념이 양쪽에서 다르게 나타난다.

```
[호출자] ──① inbound──▶ [내 게이트웨이] ──② outbound──▶ [OpenAI]
           (나 = 서버)                    (나 = 클라이언트)
```

| 종류 | ① 호출자 → 내 게이트웨이 (나=**서버**) | ② 내 게이트웨이 → OpenAI (나=**클라이언트**) |
|---|---|---|
| **connection(연결 수립)** | 호출자가 나한테 붙음(내가 accept) | **connect timeout** — 내가 OpenAI에 TCP 연결하는 시간 |
| **커넥션 풀 획득** | (서버라 해당 적음) | **pool acquisition timeout** — OpenAI용 풀에서 커넥션 빌리는 대기 |
| **read(데이터 수신)** | 호출자가 **요청 바디를 느리게** 보낼 때 (`server.tomcat.connection-timeout`) | OpenAI **응답 바이트** 대기 (read/socket) |
| **inter-token(스트리밍)** | 내가 호출자에게 **쓰며** 연결 유지(write/idle·heartbeat) | OpenAI SSE **토큰 간격** timeout (`Flux.timeout`) |
| **write(전송)** | 호출자가 **응답을 느리게 읽을 때**(slow consumer) | OpenAI에 **요청 바디 전송** 완료까지 |
| **전체 요청 수명** | **async request timeout**(`spring.mvc.async.request-timeout`, SseEmitter) | **call/overall timeout** — OpenAI 호출 전체 상한 |
| **idle(유휴)** | keep-alive idle(`server.tomcat.keep-alive-timeout`, 앞단 LB도) | 유휴 업스트림 커넥션 정리(풀) |

> 포인트 1: **read timeout은 "전체 응답 시간"이 아니라 "데이터가 한 번이라도 오면 리셋"**되는 경우가 많다. 그래서 스트리밍엔 전체 상한·inter-token을 따로 둔다.
> 포인트 2(게이트웨이 핵심): **outbound 전체 예산 < inbound 수명**이어야 한다. 안 그러면 호출자는 이미 끊었는데 나는 OpenAI에 매달리는 헛수고(→ Q8). 정석은 **deadline 전파**(→ Q7).

**꼬리질문**: connection timeout과 read timeout 중 하나만 설정한다면?
→ 둘은 다른 장애를 잡으므로 **둘 다 필수**. connection만 두면 "연결은 됐는데 응답 안 오는" 행(hang)을 못 잡고, read만 두면 대상이 죽었을 때 OS 기본 SYN 재시도(수십 초~분)까지 매달린다.

**감점 포인트**: "타임아웃은 응답이 늦으면 끊는 것" 한 문장으로 끝내는 것. **서버 쪽(inbound)과 클라이언트 쪽(outbound)을 구분 못 하면** 게이트웨이 개발자로서 깊이가 없다고 본다.

---

### Q2. HTTP 클라이언트의 기본 타임아웃은 보통 어떻게 돼 있고, 왜 위험한가요?

**모범답안**: **상당수 클라이언트의 기본값이 "무한대(0)"** 라는 게 함정이다.

- 예: Java `RestTemplate`의 기본 `SimpleClientHttpRequestFactory`는 connect/read 모두 **0(무한)**. `HttpURLConnection`도 기본 무한.
- 반대로 OkHttp는 connect/read/write 각 **10초** 기본(단 전체 call timeout은 0).

무한대가 위험한 이유: 대상이 느려지거나 멈추면 **호출 스레드가 영원히 점유**되고, 요청이 쌓이면 **스레드 풀이 고갈**돼 그 서비스 전체가 멈춘다(뒤 Q5와 연결). "기본값을 믿지 말고 **명시적으로 설정**한다"가 핵심.

**감점 포인트**: 기본값을 "알아서 적당히 잡혀 있다"고 가정. 실제로 무한대인 경우가 많아 사고의 단골 원인이다.

## 레벨 2 — 실무 (스택 전반)

### Q3. 커넥션 풀에도 타임아웃이 있죠. 풀 고갈과 어떻게 엮이나요?

**모범답안**: 풀에는 **"커넥션을 빌려오기까지 기다리는" connection-acquisition timeout**이 따로 있다(HTTP 풀, DB 풀 모두).

- 예: HikariCP `connectionTimeout` 기본 **30초** — 풀에 빈 커넥션이 없을 때 이만큼 기다리다 실패.
- 시나리오: 다운스트림이 느려짐 → 커넥션이 오래 반납 안 됨 → 풀 소진 → 새 요청은 acquisition timeout까지 대기 → **장애가 풀을 통해 번진다.**

그래서 **소켓 타임아웃(빨리 반납되게)**과 **풀 타임아웃(빨리 실패하게)**을 같이 봐야 한다. 소켓 read timeout을 짧게 둬야 커넥션이 빨리 풀로 돌아온다.

**꼬리질문**: 풀 사이즈를 키우면 해결되나?
→ 일시적 완화일 뿐. 근본은 다운스트림 지연이고, 풀을 키우면 **더 많은 스레드/커넥션이 같이 묶여** 오히려 자원만 더 태운다. 타임아웃·서킷브레이커로 **빨리 포기**하는 게 정석.

> 🔌 게이트웨이 관점: 내 **OpenAI용 outbound 커넥션 풀**이 바로 그 급소다. OpenAI가 느려지면 이 풀이 고갈되고, 그러면 **OpenAI와 무관한 다른 라우트의 요청까지** 게이트웨이가 못 받는다. → 업스트림(프로바이더)별로 풀을 격리(Q4 bulkhead).

### Q4. 타임아웃이 없거나 너무 길면 어떤 식으로 시스템 전체 장애로 번지나요?

**모범답안**: 전형적인 **cascading failure(연쇄 장애)** 시나리오.
```
다운스트림 D가 느려짐
 → D를 부르는 스레드들이 타임아웃 없이 대기
 → 호출 서비스 C의 스레드 풀/커넥션 풀 고갈
 → C가 받는 다른 (무관한) 요청까지 처리 불가
 → C를 부르는 B도 같은 식으로 고갈 → 위로 전파
```
즉 **한 다운스트림 지연이 전체로 퍼진다.** 방지책:

- **타임아웃**: 빨리 포기해서 스레드를 풀어준다 (1차 방어).
- **Bulkhead(격벽)**: 다운스트림별로 스레드/커넥션 풀을 격리 → 한 곳이 막혀도 다른 곳은 산다.
- **Circuit breaker(서킷 브레이커)**: 실패율이 높으면 호출 자체를 잠시 차단 → 죽어가는 의존성에 매달리지 않음.
- **Load shedding / 큐 상한**: 받을 수 없으면 빨리 거절(429).

**감점 포인트**: 타임아웃만 답하고 bulkhead/circuit breaker를 못 엮으면 "리질리언스 패턴" 이해가 약하다고 본다.

> 🔌 게이트웨이 관점: 게이트웨이는 **모두가 거쳐 가는 공유 길목**이라 전파의 진앙이 되기 쉽다. OpenAI 하나가 느려졌다고 게이트웨이 전체가 죽으면 안 됨 → **프로바이더/라우트/모델별 bulkhead**로 격리하고, OpenAI 실패율이 높으면 **서킷 브레이커로 차단 후 빠른 503/폴백**(→ Q13).

### Q5. 타임아웃이 났는데 사실 서버는 처리를 끝냈을 수도 있죠. 이 문제를 어떻게 다루나요?

**모범답안**: **타임아웃 ≠ 실패**다. 클라이언트가 끊었어도 서버는 요청을 정상 처리했을 수 있다(응답만 못 받음). 그래서:

- **부작용 없는(조회) 요청**은 그냥 재시도하면 됨.
- **부작용 있는(쓰기/결제) 요청**은 재시도 시 **중복 실행** 위험 → **멱등성(idempotency)** 필요.
  - 클라이언트가 **idempotency key**(고유 요청 ID)를 보내고, 서버는 같은 키면 한 번만 실행하고 이전 결과를 반환.
  - 예: 결제 API에서 타임아웃 후 재시도해도 이중 결제가 안 되도록.

**꼬리질문**: 멱등성을 어디서 보장하나?
→ 서버 측. 키를 저장(예: DB 유니크 제약 / Redis)하고 중복 키를 거르거나 같은 응답을 돌려준다. 클라이언트만 믿으면 안 된다.

**감점 포인트**: "타임아웃 나면 재시도하면 된다"고만 답. 쓰기 요청의 중복 위험·멱등성을 못 짚으면 실무 경험이 의심받는다.

> 🔌 게이트웨이 관점: OpenAI 호출이 read timeout 나도 **OpenAI는 생성을 끝내고 토큰만큼 과금**했을 수 있다. 여기서 재시도하면 **이중 과금 + 중복 요청**. 그래서 (a) outbound는 **연결을 확실히 끊어**(취소) 생성·과금을 멈추고(→ Q8), (b) OpenAI의 `idempotency key`(지원 시)를 실어 보낸다. 호출자에게도 게이트웨이가 멱등성 키를 받아 같은 응답을 돌려주는 설계가 안전.

### Q6. 타임아웃과 재시도(retry)는 어떻게 함께 설계하나요?

**모범답안**: 둘은 **곱셈으로 엮인다** — 최악 소요시간 ≈ `타임아웃 × 시도 횟수`. 그래서 무지성 재시도는 위험.

- **Exponential backoff + jitter**: 재시도 간격을 지수적으로 늘리고 **무작위(jitter)**를 더한다. jitter가 없으면 모든 클라이언트가 동시에 재시도해 **retry storm(재시도 폭주)** → 회복 중인 서버를 다시 죽인다.
- **Retry budget / 상한**: 전체 트래픽 중 재시도 비율을 제한(예: 10%). 무한 재시도 금지.
- **재시도 대상 구분**: connection timeout·5xx·네트워크 오류는 재시도 OK, **4xx(클라 잘못)·멱등성 없는 쓰기**는 재시도 금지.
- **상위 deadline 고려**: 전체 마감시간을 넘기면서까지 재시도하면 의미 없다(아래 Q7).

**감점 포인트**: jitter·retry budget 없이 "실패하면 3번 재시도" 수준. 재시도가 장애를 **증폭**시킬 수 있다는 인식이 핵심이다.

> 🔌 게이트웨이 관점: 게이트웨이가 OpenAI에 무지성 재시도하면 **이미 힘든 OpenAI에 부하를 증폭**시킨다. OpenAI가 `429`로 주는 **`Retry-After` 헤더를 존중**하고, 프로바이더별 retry budget을 둔다. 그리고 재시도는 **남은 deadline 안에서만**(→ Q7) — 호출자가 준 시간을 넘기면 재시도 의미 없음.

## 레벨 3 — 분산 시스템 (여기서 합격/불합격 갈림)

### Q7. 마이크로서비스 체인에서 타임아웃을 어떻게 설계해야 하나요?

**모범답안**: **상위 타임아웃 > 하위 타임아웃들의 합** 이 되도록, 즉 **타임아웃 예산(timeout budget)을 위에서 아래로 분배**한다.
```
A(사용자 마감 3s) → B(2.5s) → C(1.5s) → D(800ms)
   ← 위로 갈수록 여유, 아래로 갈수록 빠듯하게
```
이게 거꾸로 되면(하위가 상위보다 길면) **상위가 먼저 끊는데 하위는 계속 일하는** 낭비가 생긴다 — 자원은 쓰는데 결과는 아무도 안 받음.

**더 강한 답 — deadline propagation(데드라인 전파)**: 고정 타임아웃을 각자 박는 대신, **"언제까지"라는 절대 마감시각(deadline)을 호출에 실어 전파**한다. 각 서비스는 "남은 시간"으로 자기 타임아웃을 동적으로 계산. 이미 마감 지났으면 **호출 자체를 안 한다**(헛수고 방지). gRPC의 deadline이 이 모델.

**꼬리질문**: timeout과 deadline의 차이는?
→ timeout은 "지금부터 N초"(상대적, 각 hop마다 리셋되어 누적될 위험), deadline은 "오후 3시 0.0초까지"(절대적, 전파되며 전체 체인이 공유). deadline이 분산 환경에 더 안전.

**감점 포인트**: 각 서비스에 독립적으로 타임아웃을 박으면 된다고만 답. "상위>하위 합", deadline 전파를 못 말하면 분산 사고가 약하다고 본다.

### Q8. 클라이언트 타임아웃이 서버 처리시간보다 짧으면 서버 쪽에선 무슨 일이 생기나요?

**모범답안**: 클라이언트는 끊고 떠났지만 **서버는 그걸 모르고 계속 일한다**(기본적으로). 결과:

- 연산·DB·다운스트림 호출이 **버려질 결과를 위해 계속 자원 소모.**
- 소켓이 한쪽만 닫혀 **CLOSE_WAIT** 누적, 커넥션/스레드 누수.
- 부하가 높을수록 "아무도 안 받을 응답"을 만드느라 서버가 더 느려지는 **악순환**.

대응: **취소 전파(cancellation propagation)**. 클라이언트 연결이 끊기면 서버가 이를 감지해 작업을 중단해야 한다.

- 서블릿/Reactive: `ServletRequest`의 disconnect 감지, Reactor의 구독 취소(`doOnCancel`), gRPC의 deadline/cancel.
- 작업에 **자체 데드라인**을 줘서 클라가 이미 떠났을 시간이면 스스로 포기.

**감점 포인트**: "서버는 응답을 보내려다 실패한다" 정도. CLOSE_WAIT·자원 누수·취소 전파까지 가야 강한 답.

> 🔌 게이트웨이 관점: 호출자가 끊으면 나는 **OpenAI로 향한 outbound 호출도 같이 취소**해야 한다. 안 그러면 아무도 안 받을 토큰을 OpenAI가 계속 생성하고 **그 비용은 나한테 청구**된다. Reactor면 inbound 구독 취소가 `doOnCancel`로 전파되게 파이프라인을 잇고(취소가 outbound 연결 종료까지 내려가게), 끊긴 연결엔 생성을 멈춘다. **취소 전파 = 비용 절감**이 게이트웨이에선 직접적이다.

### Q9. 타임아웃 값은 어떻게 정하나요? (얼마로 둘 거냐)

**모범답안**: **감으로 정하지 않고 데이터(지연 분포)로 정한다.**

- 정상 응답의 **p99 / p99.9 latency**를 측정해, 그보다 약간 위로 타임아웃을 잡는다(정상 트래픽을 죽이지 않으면서 진짜 이상치만 컷).
- 너무 짧으면: 정상 요청도 죽어 가용성↓·재시도↑. 너무 길면: 장애 시 자원을 오래 잡아 전파.
- **SLA/사용자 인내심**에서 거꾸로도 잡는다(사용자 마감 3s면 그 안에 끝나도록 예산 분배).
- 고정값이 어렵다면 **adaptive timeout**(최근 지연 분포 기반 동적 조정)도 있다.

**심화 — tail latency 대응**: p99가 길어 답답하면 **hedged request(헤지)** — p95 시점에 같은 요청을 **다른 복제본에 한 번 더** 보내고 먼저 오는 걸 사용. 꼬리 지연을 깎는 기법(단 부하 증가 trade-off, 멱등성 전제).

**감점 포인트**: "한 5초 정도?" 같은 임의값. **측정 기반(p99)** 과 **자원 영향 trade-off**를 말해야 한다.

> 🔌 게이트웨이 관점: **단일 글로벌 타임아웃은 틀린 답**이다. 라우트/모델마다 지연 분포가 천차만별 — 작은 모델 응답은 수백 ms인데 reasoning 모델은 수십 초, 스트리밍은 분 단위. **라우트·모델별로 타임아웃을 다르게**(설정 외부화) 잡아야 한다. "모든 요청 30초" 같은 한 값은 짧은 건 못 지키고 긴 건 죽인다.

## 레벨 4 — LLM 서빙 맥락 (이 레포 주제와 연결)

### Q10. LLM 추론 요청은 수초~수분 걸리기도 합니다. 일반적인 30초 게이트웨이 타임아웃이 왜 문제고, 어떻게 푸나요?

**모범답안**: 긴 생성은 **단일 응답(non-stream)**으로 받으면 전체 생성이 끝날 때까지 한 바이트도 안 와서, 게이트웨이/LB의 짧은 타임아웃에 그냥 잘린다.

- 1차 해법: **스트리밍(SSE)**. 토큰이 생성되는 대로 흘려보내면 **연결이 계속 살아있어** idle 타임아웃에 안 걸리고, 사용자 체감(TTFT)도 좋아진다.
- 동시에 **read timeout을 "전체 응답"이 아니라 "토큰 간 간격(inter-token/idle)"** 기준으로 잡아야 한다(아래 Q11).
- 비동기 패턴: 아주 긴 작업은 **작업 제출 → job id → 폴링/웹훅**(OpenAI의 background 모드 같은)로 빼서 요청-응답 타임아웃에서 분리.

---

### Q11. 스트리밍(SSE)에서는 왜 평범한 read timeout을 그대로 쓰면 안 되나요?

**모범답안**: 스트리밍은 데이터가 **드문드문** 온다. "전체 응답까지 N초" 같은 flat timeout을 걸면 **정상적인 긴 생성도 죽는다.** 봐야 할 건 "전체 시간"이 아니라:

- **TTFT(첫 토큰까지)**: prefill이 길면(긴 프롬프트) 첫 토큰이 늦다 → 이걸 별도로 허용.
- **inter-token timeout(토큰 간 간격)**: "마지막 토큰 이후 X초 동안 아무것도 안 오면" 끊는다 = 진짜 행(hang)만 잡고 정상 생성은 살림.
- **하트비트/keep-alive**: 생성이 잠깐 비어도 LB가 안 끊게 주기적 신호.

**실무 함정**: **AWS ALB의 idle timeout 기본 60초**, nginx `proxy_read_timeout` 기본 60초. 스트리밍 중 토큰 간격이 이걸 넘기거나 prefill TTFT가 길면 **LB가 먼저 연결을 끊는다.** → LB idle timeout을 올리거나, 하트비트로 흐름을 유지하거나, 스트리밍으로 간격을 좁힌다.

**감점 포인트**: "스트리밍이니까 타임아웃 길게 잡으면 됨". inter-token 개념·LB idle timeout 함정을 못 짚으면 약하다.

**꼬리질문(Spring 구현편)**: Spring에서 inter-token 타임아웃을 어떻게 구현하나요? `SseEmitter`로 되나요?
→ `SseEmitter`의 timeout은 **전체(overall) 수명**이라 토큰 단위가 아니다(`spring.mvc.async.request-timeout`). inter-token은 **Reactor `Flux.timeout(Duration)`**(직전 신호 이후 다음 onNext까지 = inter-token)으로 잡는다. TTFT와 토큰 간격을 분리하려면 first/next 오버로드:
```java
openAiTokenFlux
    .timeout(
        Mono.delay(props.ttftTimeout()),            // 첫 토큰(TTFT)은 길게 (prefill 감안)
        t -> Mono.delay(props.interTokenTimeout())  // 이후 토큰 간격은 짧게
    );
```
- **yml로 되는 것**: 전체 수명(`spring.mvc.async.request-timeout`), blocking 소켓(`spring.http.client.*`, Boot 3.4+).
- **yml로 안 되는 것**: inter-token(특정 스트림의 원소 간격이라 전역 설정 대상이 아님) → 연산자(코드). 단 **Duration 값만 `@ConfigurationProperties`로 yml 관리**하는 게 정석.
- MVC `SseEmitter`만 쓴다면 inter-token은 **watchdog/heartbeat로 직접** 구현.

---

### Q12. 자체 서빙(vLLM 등)에서 요청이 큐에 대기할 수도 있습니다. 타임아웃을 어디에 둬야 하나요?

**모범답안**: LLM 요청의 지연은 **큐 대기 + prefill + decode**로 쪼개진다. 단순 read timeout 하나로는 부족.

- **큐 대기(queue) 시간**: 동시 요청이 KV 캐시 풀을 넘으면 요청이 큐에 묶인다 → "큐에서 X초 이상이면 거절"하는 admission/queue timeout이 필요(무한 대기 방지, 빠른 429).
- **TTFT 기준 타임아웃**: 클라이언트 read timeout은 "첫 토큰까지"를 기준으로, 큐+prefill 최악을 감안해 잡는다.
- **전체 상한**: 폭주 방지를 위한 생성 전체 max time / max tokens.

> 결국 Q7의 "타임아웃 예산"을 LLM 단계(큐/prefill/decode)에 맞게 분배하는 문제다. 부하가 높을 때 **빨리 거절(load shedding)**하는 게 모두를 매달리게 하는 것보다 낫다.

### Q13. 게이트웨이가 타임아웃 시 다른 프로바이더로 폴백(fallback)한다면, 타임아웃을 어떻게 설계하나요?

**모범답안**: 폴백은 타임아웃과 **예산을 나눠 써야** 한다. 핵심은 **1차 시도를 빨리 포기(fast-fail)해야 폴백할 시간이 남는다**는 것.
```
호출자 마감 10s
 ├ 1차(OpenAI)  timeout 6s  → 실패/타임아웃
 └ 2차(폴백)    남은 4s 안에서 시도
```

- 1차 타임아웃을 호출자 마감과 똑같이(10s) 잡으면 **폴백할 시간이 0** → 폴백이 무의미.
- 그래서 **1차는 공격적으로 짧게**, 남은 deadline으로 2차를 호출(→ Q7 deadline 전파와 같은 원리).
- **무엇으로 폴백을 트리거**하나: connection timeout·5xx·429·서킷 오픈은 폴백 OK. 하지만 **이미 토큰이 흐르기 시작한 스트리밍**은 중간 폴백이 어렵다(→ Q14).
- 멱등성/일관성: 1차가 사실 성공했는데 타임아웃으로 오인하고 2차도 부르면 **양쪽 다 과금**될 수 있다(→ Q5).

**감점 포인트**: "타임아웃 나면 다른 모델 부르면 됨"만 답. **1차를 짧게 잡아 폴백 예산을 확보**한다는 점, 스트리밍 중엔 폴백이 까다롭다는 점을 못 짚으면 약하다.

### Q14. 스트리밍 도중 OpenAI 연결이 끊기면(부분 응답) 게이트웨이는 어떻게 처리하나요?

**모범답안**: 이게 스트리밍 특유의 어려운 지점이다. **이미 호출자에게 토큰 일부를 보낸 뒤** 업스트림이 죽으면:

- **깔끔한 재시도가 불가능**하다 — 처음부터 다시 하면 호출자는 같은 앞부분을 두 번 받는다. 그래서 보통 **중간 폴백/재시도는 포기**하고 스트림을 **에러로 종료**한다.
- SSE에선 HTTP 상태코드를 이미 200으로 보내버린 뒤라, 실패를 **본문 안의 에러 이벤트**(예: `event: error` 또는 `data: {"error": ...}`)로 알려야 한다. 헤더로는 못 바꾼다.
- **부분 usage/과금**: 거기까지 생성된 토큰은 과금됐을 수 있으니, 가능한 만큼 부분 usage를 집계·기록.
- 첫 토큰 **이전**(아직 아무것도 안 보냄)이라면 아직 상태코드 전이라 → 그땐 깔끔하게 5xx/폴백 가능. **"첫 토큰을 보냈는가"가 분기점.**

**꼬리질문**: inter-token timeout이 스트림 중간에 걸리면?
→ 그 시점까지의 토큰은 이미 호출자에게 갔고, 더는 안 오므로 **에러 이벤트로 스트림 종료**. 호출자 입장에선 "부분 응답 + 끊김"을 받는다. 그래서 클라이언트도 부분 응답·중단을 처리할 수 있게 설계돼야 한다.

**감점 포인트**: "재시도하면 된다". 스트리밍은 **상태코드를 이미 보낸 뒤**라 재시도·헤더 변경이 안 되고, "첫 토큰 전/후"로 처리가 갈린다는 걸 모르면 스트리밍 실패 의미론을 모르는 것.

### Q15. 주요 LLM SDK의 디폴트 타임아웃은 얼마고, 게이트웨이에선 어떻게 설정하나요?

**모범답안**: 대부분의 SDK 디폴트가 **너무 길다(또는 없다)** — 그대로 쓰면 안 된다.

| SDK (Python) | 디폴트 타임아웃 | connect | max_retries |
|---|---|---|---|
| **OpenAI** | **600초(10분)** | 5초 | 2 |
| **Anthropic** | **600초(10분)** + 비스트림은 `max_tokens` 기반 동적 조정·초과 시 에러 | 5초 | 2 |
| **Google GenAI** | **없음(None)** — 명시 안 하면 미설정(단위 ms) | — | — |

> 즉 OpenAI/Anthropic은 **10분**, GenAI는 **무제한**이 디폴트. 게이트웨이엔 둘 다 부적합 → **명시적으로 override**.

**꼬리질문**: 그래서 당신은 얼마로 둘 건가요?
→ 단일값이 아니라 **양쪽(inbound/outbound)·워크로드별로** 잡는다 (Q1 표와 같은 축으로 비교):

| 종류 | ① 호출자 → 내 게이트웨이 (나=서버, inbound) | ② 내 게이트웨이 → OpenAI (나=클라, outbound) |
|---|---|---|
| **connection(연결 수립)** | (accept — 직접 설정 거의 없음) | **connect 2~3s** (빨리 실패) |
| **커넥션 풀 획득** | (서버라 해당 적음) | **수백 ms~2s** (풀 크기에 맞게) |
| **read(데이터 수신)** | 요청 바디 **5~10s** | 임베딩 **10s** / 짧은 chat **30~60s** / 이미지·긴 작업 **60~120s** |
| **inter-token(스트리밍)** | 호출자에 write하며 유지 + **heartbeat** | **15~30s** (httpx `read`가 청크 간 대기 역할) |
| **write(전송)** | slow consumer 대비(짧게) | 요청 바디 전송 **5~10s** |
| **전체 요청 수명** | non-stream **30~90s**(라우트별) / stream **길게+inter-token으로 제어** | non-stream은 inbound 예산 안(≈read), stream은 inter-token에 위임 |
| **idle(유휴)** | keep-alive **65~75s** · 앞단 LB(ALB) **120~300s/heartbeat** | 업스트림 풀 idle 정리 |
| **재시도 / 예산** | (호출자 멱등키 수용) | **max_retries 0~1** · backoff+jitter · budget≤10% · **inbound ≥ outbound + 50~200ms** |

> 핵심 구조: **connect 짧게 / read·inter-token은 워크로드별 / 전체는 inbound 예산 안에 / 재시도는 게이트웨이 한 곳 / 최종은 p99로 보정.**

**감점 포인트**: "OpenAI 디폴트가 10분이니 그대로 쓴다". 디폴트가 게이트웨이엔 길다는 점, 워크로드/위치별로 분리한다는 점을 못 짚으면 약하다.

## 한 장 요약 (면접 직전 복습용)

```
0. 게이트웨이는 양면: inbound(나=서버) / outbound(나=클라이언트). outbound 예산 < inbound 수명
1. 종류: connection / read / write / 전체 / idle — 각각 다른 장애를 잡는다 (둘 다 설정)
2. 함정: 기본값이 무한대인 클라이언트 많음 → 반드시 명시
3. 자원: 타임아웃 없으면 스레드·커넥션 풀 고갈 → cascading failure
         → bulkhead(프로바이더별) / circuit breaker / load shedding 으로 격리·차단
4. 재시도: timeout × 시도횟수. backoff + jitter + retry budget, 멱등성(쓰기). Retry-After 존중
5. 분산: 상위 > 하위 합. deadline propagation(절대 마감 전파, gRPC식)
6. 취소: 클라가 끊으면 outbound(OpenAI)도 끊어야 = 비용 절감. 안 그러면 CLOSE_WAIT·자원·과금 낭비
7. 값 정하기: 감 아니고 p99 측정 기반 + tail은 hedging. 라우트/모델별로 다르게(단일 글로벌 X)
8. LLM: 긴 생성은 스트리밍, read timeout은 inter-token 기준, ALB/nginx idle 60s 함정
        Spring: 전체=SseEmitter/yml, inter-token=Flux.timeout(코드, 값만 yml)
9. 폴백: 1차를 짧게 잡아야 폴백 예산 확보. 스트리밍 중간 폴백은 어려움
10. 스트리밍 실패: "첫 토큰 전/후"가 분기점. 보낸 뒤엔 재시도·헤더변경 불가 → 본문 에러 이벤트로 종료
11. SDK 디폴트: OpenAI·Anthropic 10분 / GenAI 없음 → 게이트웨이는 override. connect 2~3s, stream read(=inter-token) 15~30s, max_retries=0
```

> 떨어지는 답 vs 붙는 답의 차이: **정의를 말하느냐 vs "이게 없으면 시스템이 어떻게 무너지는지"를 말하느냐.** 면접관은 후자를 본다. (게이트웨이라면 한 겹 더: **inbound/outbound 양면 + 비용**까지.)
