# 해시 (Hash)

해시는 임의 길이의 입력을 고정 길이의 정수로 바꾸는 함수다.  
같은 입력은 항상 같은 출력이 나와야 하고, 다른 입력은 될 수 있으면 다른 출력이 나와야 한다.

| 용도 | 입력 | 출력 | 왜 쓰나 |
|---|---|---|---|
| 해시 테이블 | 키 문자열 | 버킷 인덱스 | O(1) 조회 |
| 비밀번호 | `password123` | `$2a$10$N9qo...` | 원문 안 저장, 검증만 |
| 체크섬 | 파일 전체 | 32자리 hex | 파일 무결성 확인 |
| git commit | 커밋 내용 | `a1b2c3d...` | 내용이 같으면 같은 해시 |

핵심 성질:

- **결정적** — 같은 입력은 항상 같은 출력
- **고정 길이** — 입력이 1글자든 1GB든 출력 크기는 같음
- **역방향 불가** (암호화 해시만) — 출력에서 입력을 유추할 수 없음

> 해시 테이블에서 쓰는 해시는 "빠르고 골고루 퍼지기만 하면" 된다.  
> 비밀번호 저장에 쓰는 해시(bcrypt 등)는 "역방향 불가"가 핵심이다.  
> 같은 단어지만 용도가 다르면 요구 조건이 다르다.

## 객체의 equals와 hashCode

해시 테이블(HashMap, HashSet)에 객체를 넣으려면,  
객체가 **같은지 판별**하는 기준이 있어야 한다.  
그게 `equals()`와 `hashCode()`다.

### 왜 둘 다 필요한가

HashMap은 조회할 때 두 단계를 거친다:

```text
1. hashCode() → 버킷 인덱스 찾기 (어느 줄에 있는가?)
2. equals() → 버킷 안에서 실제 키 비교 (이 줄 안에서 정확히 어느 놈인가?)
```

```text
get(user)
1. user.hashCode() % 16 = 7   → bucket[7]로 이동
2. bucket[7]: (user1, ...), (user2, ...), ...
   user.equals(user1)? → false
   user.equals(user2)? → true → 찾음
```

`hashCode()`가 같아야 같은 버킷에 들어가고,  
`equals()`가 같아야 실제로 같은 객체로 인식한다.

### 계약 — equals와 hashCode의 규칙

| 규칙 | 의미 |
|---|---|
| equals가 true면 | hashCode도 **같아야 한다** |
| hashCode가 같다고 | equals가 true일 필요는 **없다** (충돌 허용) |
| equals가 false면 | hashCode는 같아도 되고 달라도 된다 |

> **가장 흔한 버그**: `equals()`만 오버라이딩하고 `hashCode()`를 안 하면,  
> 같은 객체가 다른 버킷에 들어가서 `get()`이 `null`을 반환한다.

### 잘못된 예

```kotlin
data class User(val id: Long, val name: String)

// case 1: equals만 오버라이딩 (hashCode 안 함)
class User(val id: Long, val name: String) {
    override fun equals(other: Any?): Boolean =
        other is User && id == other.id
    // hashCode() 없음 → 기본 Object.hashCode() = 메모리 주소 기반
}

val map = HashMap<User, String>()
val user1 = User(1, "dan")
val user2 = User(1, "dan")  // 논리적으로 같은 객체

map[user1] = "admin"
map[user2]  // → null! user1과 user2가 hashCode가 달라서 다른 버킷에 들어감
```

### 올바른 예 — data class

```kotlin
data class User(val id: Long, val name: String)
// data class는 equals() + hashCode()를 자동 생성
// 같은 프로퍼티 값 → 같은 hashCode, equals true

val map = HashMap<User, String>()
val user1 = User(1, "dan")
val user2 = User(1, "dan")  // 같은 내용

map[user1] = "admin"
map[user2]  // → "admin" ✅ 같은 버킷, equals true
```

> Kotlin `data class`는 `equals()` + `hashCode()`를 자동으로 생성한다.  
> Java `record`도 마찬가지다.  
> 직접 `equals`/`hashCode`를 오버라이딩할 일은 거의 없다 — data class를 쓰면 된다.

### hashCode 구현 가이드

직접 구현해야 한다면 (Java):

```java
// Objects.hash() 사용 — 가장 간단
@Override
public int hashCode() {
    return Objects.hash(id, name);
}
```

규칙:

- `equals()`에서 비교하는 **모든 필드**를 `hashCode()`에도 포함
- `equals()`에서 안 쓰는 필드를 `hashCode()`에 넣으면 안 됨  
  (equals가 false인데 hashCode가 같아질 수 있음 — 문제는 아니지만 불필요한 충돌)
- **가변 필드**를 hashCode에 쓰면 안 됨  
  (객체를 HashMap에 넣은 뒤 필드를 바꾸면 hashCode가 바뀌어서 조회 불가)

```kotlin
// 나쁜 예 — 가변 필드를 hashCode에 사용
class User(var id: Long) {
    override fun equals(other: Any?) = other is User && id == other.id
    override fun hashCode() = id.hashCode()
}

val map = HashMap<User, String>()
val user = User(1)
map[user] = "admin"
user.id = 2  // hashCode 변경!
map[user]   // → null! 다른 버킷에 있음
```

> **해시 테이블에 넣은 객체의 키를 바꾸면 안 된다**.  
> hashCode가 바뀌어서 다른 버킷으로 가야 하는데, 이미 옛 버킷에 남아 있다.  
> 불변 객체(immutable)를 키로 쓰는 것이 안전하다.

## 실무 예제

### 캐싱 — HashMap으로 결과 캐시

```kotlin
data class CacheKey(val userId: Long, val date: LocalDate)

val cache = HashMap<CacheKey, UserProfile>()

fun getProfile(userId: Long, date: LocalDate): UserProfile {
    val key = CacheKey(userId, date)
    return cache.getOrPut(key) {
        profileRepository.findByIdAndDate(userId, date)  // cache miss 시에만 DB 조회
    }
}
```

`CacheKey`가 `data class`이므로 `equals`/`hashCode`가 자동 생성된다.  
같은 `userId` + `date` 조합은 같은 버킷에 들어가고 `equals`로 같은 키로 인식된다.

### 중복 제거 — HashSet

```kotlin
data class Order(val orderId: String, val amount: BigDecimal)

val orders = listOf(
    Order("A001", BigDecimal("100")),
    Order("A001", BigDecimal("100")),  // 중복
    Order("A002", BigDecimal("200")),
)

val unique = orders.toSet()  // HashSet 사용
// → [Order("A001", 100), Order("A002", 200)]
// orderId + amount가 같으면 같은 객체로 인식 → 중복 제거
```

`HashSet`은 내부적으로 `HashMap`의 키만 쓴다.  
`equals`/`hashCode`가 같으면 같은 원소로 판단한다.

### 잘못된 키 사용 — 리스트를 키로

```kotlin
val list = mutableListOf(1, 2, 3)
val map = HashMap<List<Int>, String>()

map[list] = "data"
list.add(4)  // 리스트 내용 변경 → hashCode 변경

map[list]  // → null! hashCode가 바뀌어서 다른 버킷에 있음
map[mutableListOf(1, 2, 3)]  // → null! 이것도 다름 (이미 1,2,3,4가 됨)
```

> **가변 객체를 HashMap 키로 쓰면 안 된다**.  
> `MutableList` 대신 `List` (불변)를 키로 쓰거나,  
> `data class`의 불변 필드만 키에 넣어야 한다.

### 정리 — 언제 equals/hashCode를 직접 신경 써야 하나

| 상황 | 필요 |
|---|---|
| `data class` 사용 | **불필요** — 자동 생성 |
| `record` 사용 | **불필요** — 자동 생성 |
| 일반 class + HashMap/HashSet 키 | **필요** — 직접 오버라이딩 |
| 일반 class + HashMap/HashSet 값 | **불필요** — 값은 equals/hashCode 안 쓰임 |
| JPA `@Entity` | **주의** — 엔티티 식별자 기반 equals/hashCode 필요 (아래 참조) |

### JPA 엔티티의 equals/hashCode

JPA 엔티티는 기본적으로 `@Entity` 클래스인데,  
`data class`로 만들면 프록시·지연 로딩 문제가 생긴다.

```kotlin
// 나쁜 예 — data class로 엔티티 정의
@Entity
data class User(
    @Id @GeneratedValue val id: Long? = null,
    val name: String,
)
// 문제: Hibernate 프록시와 equals 호환 안 됨, 
// 지연 로딩 시 필드가 null일 수 있음

// 올바른 예 — 일반 class + 식별자 기반 equals/hashCode
@Entity
class User(
    @Id @GeneratedValue
    val id: Long? = null,
    val name: String,
) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is User) return false
        // id가 null이면 (아직 persist 안 됨) 동일성 비교만
        return id != null && id == other.id
    }

    override fun hashCode(): Int {
        // id가 null이면 0, 아니면 id.hashCode()
        // 주의: id가 persist 후에 바뀔 수 있으므로,
        // 영속화 전후로 hashCode가 바뀌지 않게 주의
        return id?.hashCode() ?: 0
    }
}
```

> JPA 엔티티의 equals/hashCode는 **식별자(id) 기반**이 정석이다.  
> `data class`의 전체 필드 비교는 지연 로딩·프록시와 충돌한다.  
> 자세한 것은 [API Key 저장](./2607-api-key-storage.md)의 엔티티 설계 참조.
