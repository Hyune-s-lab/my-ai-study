# 모의면접 — 타임아웃 (Timeout)

> 면접관이 타임아웃으로 보려는 것은 **용어 암기가 아니라**: 장애가 어떻게 **전파(cascading failure)**되는지, **자원(스레드·커넥션)**이 어떻게 고갈되는지, 분산 환경에서 **타임아웃을 어떻게 설계**하는지에 대한 사고력이다.
> 형식: **Q(질문) → 모범답안 → 꼬리질문 → 감점 포인트(이렇게 답하면 약하다)**.

---

## 레벨 1 — 개념

### Q1. 타임아웃의 종류를 설명해보세요.

**모범답안**: 한 번의 외부 호출에도 타임아웃이 여러 단계로 나뉜다.

| 종류 | 무엇을 기다리다 끊나 | 주로 잡는 장애 |
|---|---|---|
| **connection timeout** | TCP 연결(핸드셰이크) 수립까지 | 대상이 죽음·네트워크 단절·방화벽 |
| **read(socket) timeout** | 연결 후 **데이터(바이트) 한 번** 도착까지 | 서버가 받아놓고 응답 안 함(행) |
| **write timeout** | 요청 바디 전송 완료까지 | 느린 수신측·역압(backpressure) |
| **(전체) request/call timeout** | 요청 시작~완료 **전 구간** | 위를 다 합친 상한선 |
| **idle timeout** | 연결에서 **무동작** 지속 시간 | 유휴 커넥션 정리(keep-alive) |

> 포인트: read timeout은 "전체 응답 시간"이 아니라 **"데이터가 한 번이라도 오면 리셋"**되는 경우가 많다. 그래서 스트리밍/대용량엔 전체 상한(call timeout)을 따로 둬야 한다.

**꼬리질문**: connection timeout과 read timeout 중 하나만 설정한다면?
→ 둘은 다른 장애를 잡으므로 **둘 다 필수**. connection만 두면 "연결은 됐는데 응답 안 오는" 행(hang)을 못 잡고, read만 두면 대상이 죽었을 때 OS 기본 SYN 재시도(수십 초~분)까지 매달린다.

**감점 포인트**: "타임아웃은 응답이 늦으면 끊는 것" 한 문장으로 끝내는 것. 단계 구분을 못 하면 깊이가 없다고 본다.

---

### Q2. HTTP 클라이언트의 기본 타임아웃은 보통 어떻게 돼 있고, 왜 위험한가요?

**모범답안**: **상당수 클라이언트의 기본값이 "무한대(0)"** 라는 게 함정이다.
- 예: Java `RestTemplate`의 기본 `SimpleClientHttpRequestFactory`는 connect/read 모두 **0(무한)**. `HttpURLConnection`도 기본 무한.
- 반대로 OkHttp는 connect/read/write 각 **10초** 기본(단 전체 call timeout은 0).

무한대가 위험한 이유: 대상이 느려지거나 멈추면 **호출 스레드가 영원히 점유**되고, 요청이 쌓이면 **스레드 풀이 고갈**돼 그 서비스 전체가 멈춘다(뒤 Q5와 연결). "기본값을 믿지 말고 **명시적으로 설정**한다"가 핵심.

**감점 포인트**: 기본값을 "알아서 적당히 잡혀 있다"고 가정. 실제로 무한대인 경우가 많아 사고의 단골 원인이다.

## 레벨 2 — 실무 (스택 전반)

### Q3. 커넥션 풀에도 타임아웃이 있죠. 풀 고갈과 어떻게 엮이나요?

**모범답안**: 풀에는 **"커넥션을 빌려오기까지 기다리는" connection-acquisition timeout**이 따로 있다(HTTP 풀, DB 풀 모두).
- 예: HikariCP `connectionTimeout` 기본 **30초** — 풀에 빈 커넥션이 없을 때 이만큼 기다리다 실패.
- 시나리오: 다운스트림이 느려짐 → 커넥션이 오래 반납 안 됨 → 풀 소진 → 새 요청은 acquisition timeout까지 대기 → **장애가 풀을 통해 번진다.**

그래서 **소켓 타임아웃(빨리 반납되게)**과 **풀 타임아웃(빨리 실패하게)**을 같이 봐야 한다. 소켓 read timeout을 짧게 둬야 커넥션이 빨리 풀로 돌아온다.

**꼬리질문**: 풀 사이즈를 키우면 해결되나?
→ 일시적 완화일 뿐. 근본은 다운스트림 지연이고, 풀을 키우면 **더 많은 스레드/커넥션이 같이 묶여** 오히려 자원만 더 태운다. 타임아웃·서킷브레이커로 **빨리 포기**하는 게 정석.

---

### Q4. 타임아웃이 없거나 너무 길면 어떤 식으로 시스템 전체 장애로 번지나요?

**모범답안**: 전형적인 **cascading failure(연쇄 장애)** 시나리오.
```
다운스트림 D가 느려짐
 → D를 부르는 스레드들이 타임아웃 없이 대기
 → 호출 서비스 C의 스레드 풀/커넥션 풀 고갈
 → C가 받는 다른 (무관한) 요청까지 처리 불가
 → C를 부르는 B도 같은 식으로 고갈 → 위로 전파
```
즉 **한 다운스트림 지연이 전체로 퍼진다.** 방지책:
- **타임아웃**: 빨리 포기해서 스레드를 풀어준다 (1차 방어).
- **Bulkhead(격벽)**: 다운스트림별로 스레드/커넥션 풀을 격리 → 한 곳이 막혀도 다른 곳은 산다.
- **Circuit breaker(서킷 브레이커)**: 실패율이 높으면 호출 자체를 잠시 차단 → 죽어가는 의존성에 매달리지 않음.
- **Load shedding / 큐 상한**: 받을 수 없으면 빨리 거절(429).

**감점 포인트**: 타임아웃만 답하고 bulkhead/circuit breaker를 못 엮으면 "리질리언스 패턴" 이해가 약하다고 본다.

---

### Q5. 타임아웃이 났는데 사실 서버는 처리를 끝냈을 수도 있죠. 이 문제를 어떻게 다루나요?

**모범답안**: **타임아웃 ≠ 실패**다. 클라이언트가 끊었어도 서버는 요청을 정상 처리했을 수 있다(응답만 못 받음). 그래서:
- **부작용 없는(조회) 요청**은 그냥 재시도하면 됨.
- **부작용 있는(쓰기/결제) 요청**은 재시도 시 **중복 실행** 위험 → **멱등성(idempotency)** 필요.
  - 클라이언트가 **idempotency key**(고유 요청 ID)를 보내고, 서버는 같은 키면 한 번만 실행하고 이전 결과를 반환.
  - 예: 결제 API에서 타임아웃 후 재시도해도 이중 결제가 안 되도록.

**꼬리질문**: 멱등성을 어디서 보장하나?
→ 서버 측. 키를 저장(예: DB 유니크 제약 / Redis)하고 중복 키를 거르거나 같은 응답을 돌려준다. 클라이언트만 믿으면 안 된다.

**감점 포인트**: "타임아웃 나면 재시도하면 된다"고만 답. 쓰기 요청의 중복 위험·멱등성을 못 짚으면 실무 경험이 의심받는다.

---

### Q6. 타임아웃과 재시도(retry)는 어떻게 함께 설계하나요?

**모범답안**: 둘은 **곱셈으로 엮인다** — 최악 소요시간 ≈ `타임아웃 × 시도 횟수`. 그래서 무지성 재시도는 위험.
- **Exponential backoff + jitter**: 재시도 간격을 지수적으로 늘리고 **무작위(jitter)**를 더한다. jitter가 없으면 모든 클라이언트가 동시에 재시도해 **retry storm(재시도 폭주)** → 회복 중인 서버를 다시 죽인다.
- **Retry budget / 상한**: 전체 트래픽 중 재시도 비율을 제한(예: 10%). 무한 재시도 금지.
- **재시도 대상 구분**: connection timeout·5xx·네트워크 오류는 재시도 OK, **4xx(클라 잘못)·멱등성 없는 쓰기**는 재시도 금지.
- **상위 deadline 고려**: 전체 마감시간을 넘기면서까지 재시도하면 의미 없다(아래 Q7).

**감점 포인트**: jitter·retry budget 없이 "실패하면 3번 재시도" 수준. 재시도가 장애를 **증폭**시킬 수 있다는 인식이 핵심이다.

## 레벨 3 — 분산 시스템 (여기서 합격/불합격 갈림)

### Q7. 마이크로서비스 체인에서 타임아웃을 어떻게 설계해야 하나요?

**모범답안**: **상위 타임아웃 > 하위 타임아웃들의 합** 이 되도록, 즉 **타임아웃 예산(timeout budget)을 위에서 아래로 분배**한다.
```
A(사용자 마감 3s) → B(2.5s) → C(1.5s) → D(800ms)
   ← 위로 갈수록 여유, 아래로 갈수록 빠듯하게
```
이게 거꾸로 되면(하위가 상위보다 길면) **상위가 먼저 끊는데 하위는 계속 일하는** 낭비가 생긴다 — 자원은 쓰는데 결과는 아무도 안 받음.

**더 강한 답 — deadline propagation(데드라인 전파)**: 고정 타임아웃을 각자 박는 대신, **"언제까지"라는 절대 마감시각(deadline)을 호출에 실어 전파**한다. 각 서비스는 "남은 시간"으로 자기 타임아웃을 동적으로 계산. 이미 마감 지났으면 **호출 자체를 안 한다**(헛수고 방지). gRPC의 deadline이 이 모델.

**꼬리질문**: timeout과 deadline의 차이는?
→ timeout은 "지금부터 N초"(상대적, 각 hop마다 리셋되어 누적될 위험), deadline은 "오후 3시 0.0초까지"(절대적, 전파되며 전체 체인이 공유). deadline이 분산 환경에 더 안전.

**감점 포인트**: 각 서비스에 독립적으로 타임아웃을 박으면 된다고만 답. "상위>하위 합", deadline 전파를 못 말하면 분산 사고가 약하다고 본다.

---

### Q8. 클라이언트 타임아웃이 서버 처리시간보다 짧으면 서버 쪽에선 무슨 일이 생기나요?

**모범답안**: 클라이언트는 끊고 떠났지만 **서버는 그걸 모르고 계속 일한다**(기본적으로). 결과:
- 연산·DB·다운스트림 호출이 **버려질 결과를 위해 계속 자원 소모.**
- 소켓이 한쪽만 닫혀 **CLOSE_WAIT** 누적, 커넥션/스레드 누수.
- 부하가 높을수록 "아무도 안 받을 응답"을 만드느라 서버가 더 느려지는 **악순환**.

대응: **취소 전파(cancellation propagation)**. 클라이언트 연결이 끊기면 서버가 이를 감지해 작업을 중단해야 한다.
- 서블릿/Reactive: `ServletRequest`의 disconnect 감지, Reactor의 구독 취소(`doOnCancel`), gRPC의 deadline/cancel.
- 작업에 **자체 데드라인**을 줘서 클라가 이미 떠났을 시간이면 스스로 포기.

**감점 포인트**: "서버는 응답을 보내려다 실패한다" 정도. CLOSE_WAIT·자원 누수·취소 전파까지 가야 강한 답.

---

### Q9. 타임아웃 값은 어떻게 정하나요? (얼마로 둘 거냐)

**모범답안**: **감으로 정하지 않고 데이터(지연 분포)로 정한다.**
- 정상 응답의 **p99 / p99.9 latency**를 측정해, 그보다 약간 위로 타임아웃을 잡는다(정상 트래픽을 죽이지 않으면서 진짜 이상치만 컷).
- 너무 짧으면: 정상 요청도 죽어 가용성↓·재시도↑. 너무 길면: 장애 시 자원을 오래 잡아 전파.
- **SLA/사용자 인내심**에서 거꾸로도 잡는다(사용자 마감 3s면 그 안에 끝나도록 예산 분배).
- 고정값이 어렵다면 **adaptive timeout**(최근 지연 분포 기반 동적 조정)도 있다.

**심화 — tail latency 대응**: p99가 길어 답답하면 **hedged request(헤지)** — p95 시점에 같은 요청을 **다른 복제본에 한 번 더** 보내고 먼저 오는 걸 사용. 꼬리 지연을 깎는 기법(단 부하 증가 trade-off, 멱등성 전제).

**감점 포인트**: "한 5초 정도?" 같은 임의값. **측정 기반(p99)** 과 **자원 영향 trade-off**를 말해야 한다.

## 레벨 4 — LLM 서빙 맥락 (이 레포 주제와 연결)

### Q10. LLM 추론 요청은 수초~수분 걸리기도 합니다. 일반적인 30초 게이트웨이 타임아웃이 왜 문제고, 어떻게 푸나요?

**모범답안**: 긴 생성은 **단일 응답(non-stream)**으로 받으면 전체 생성이 끝날 때까지 한 바이트도 안 와서, 게이트웨이/LB의 짧은 타임아웃에 그냥 잘린다.
- 1차 해법: **스트리밍(SSE)**. 토큰이 생성되는 대로 흘려보내면 **연결이 계속 살아있어** idle 타임아웃에 안 걸리고, 사용자 체감(TTFT)도 좋아진다.
- 동시에 **read timeout을 "전체 응답"이 아니라 "토큰 간 간격(inter-token/idle)"** 기준으로 잡아야 한다(아래 Q11).
- 비동기 패턴: 아주 긴 작업은 **작업 제출 → job id → 폴링/웹훅**(OpenAI의 background 모드 같은)로 빼서 요청-응답 타임아웃에서 분리.

---

### Q11. 스트리밍(SSE)에서는 왜 평범한 read timeout을 그대로 쓰면 안 되나요?

**모범답안**: 스트리밍은 데이터가 **드문드문** 온다. "전체 응답까지 N초" 같은 flat timeout을 걸면 **정상적인 긴 생성도 죽는다.** 봐야 할 건 "전체 시간"이 아니라:
- **TTFT(첫 토큰까지)**: prefill이 길면(긴 프롬프트) 첫 토큰이 늦다 → 이걸 별도로 허용.
- **inter-token timeout(토큰 간 간격)**: "마지막 토큰 이후 X초 동안 아무것도 안 오면" 끊는다 = 진짜 행(hang)만 잡고 정상 생성은 살림.
- **하트비트/keep-alive**: 생성이 잠깐 비어도 LB가 안 끊게 주기적 신호.

**실무 함정**: **AWS ALB의 idle timeout 기본 60초**, nginx `proxy_read_timeout` 기본 60초. 스트리밍 중 토큰 간격이 이걸 넘기거나 prefill TTFT가 길면 **LB가 먼저 연결을 끊는다.** → LB idle timeout을 올리거나, 하트비트로 흐름을 유지하거나, 스트리밍으로 간격을 좁힌다.

**감점 포인트**: "스트리밍이니까 타임아웃 길게 잡으면 됨". inter-token 개념·LB idle timeout 함정을 못 짚으면 약하다.

---

### Q12. 자체 서빙(vLLM 등)에서 요청이 큐에 대기할 수도 있습니다. 타임아웃을 어디에 둬야 하나요?

**모범답안**: LLM 요청의 지연은 **큐 대기 + prefill + decode**로 쪼개진다. 단순 read timeout 하나로는 부족.
- **큐 대기(queue) 시간**: 동시 요청이 KV 캐시 풀을 넘으면 요청이 큐에 묶인다 → "큐에서 X초 이상이면 거절"하는 admission/queue timeout이 필요(무한 대기 방지, 빠른 429).
- **TTFT 기준 타임아웃**: 클라이언트 read timeout은 "첫 토큰까지"를 기준으로, 큐+prefill 최악을 감안해 잡는다.
- **전체 상한**: 폭주 방지를 위한 생성 전체 max time / max tokens.

> 결국 Q7의 "타임아웃 예산"을 LLM 단계(큐/prefill/decode)에 맞게 분배하는 문제다. 부하가 높을 때 **빨리 거절(load shedding)**하는 게 모두를 매달리게 하는 것보다 낫다.

## 한 장 요약 (면접 직전 복습용)

```
1. 종류: connection / read / write / 전체 / idle — 각각 다른 장애를 잡는다 (둘 다 설정)
2. 함정: 기본값이 무한대인 클라이언트 많음 → 반드시 명시
3. 자원: 타임아웃 없으면 스레드·커넥션 풀 고갈 → cascading failure
         → bulkhead / circuit breaker / load shedding 으로 격리·차단
4. 재시도: timeout × 시도횟수. backoff + jitter + retry budget, 멱등성(쓰기)
5. 분산: 상위 > 하위 합. deadline propagation(절대 마감 전파, gRPC식)
6. 취소: 클라가 끊으면 서버도 멈춰야(취소 전파), 안 그러면 CLOSE_WAIT·자원 누수
7. 값 정하기: 감 아니고 p99 측정 기반 + tail은 hedging
8. LLM: 긴 생성은 스트리밍, read timeout은 inter-token 기준,
        ALB/nginx idle 60s 함정, 큐 대기엔 admission timeout
```

> 떨어지는 답 vs 붙는 답의 차이: **정의를 말하느냐 vs "이게 없으면 시스템이 어떻게 무너지는지"를 말하느냐.** 면접관은 후자를 본다.
