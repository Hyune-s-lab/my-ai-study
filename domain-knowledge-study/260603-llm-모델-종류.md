# LLM 모델 종류 — open-weight vs closed, 그리고 선택 축들

> 서비스 개발자가 "어떤 모델을 쓸까" 정할 때 던지는 분류 기준 정리. self-hosting을 한다면 결국 [KV 캐시](./260601-kv-cache-기초.md)·VRAM 이야기로 이어진다.

## 1. 요약

### 1.0 가장 쉽게

> 모델을 고를 때 가장 먼저 갈리는 질문은 **"가중치 파일을 받을 수 있나?"** 다. 받을 수 있으면 **open-weight**(직접 서빙 가능), 못 받으면 **closed**(API로만 사용).

**핵심 4개 축:**
1. **접근**: open-weight(다운로드·직접 서빙) vs closed(API 전용)
2. **훈련 단계**: base(원석) vs instruct(지시 따름) — 챗봇/RAG엔 거의 항상 instruct
3. **아키텍처**: dense(전부 활성) vs MoE(일부 전문가만 활성)
4. **정밀도 변형**: 같은 가중치의 FP16 / 양자화(AWQ·GPTQ·GGUF) 버전

> 용어 주의: 여기서 "가중치(weights)" = **훈련으로 학습돼 디스크에 저장된 모델 본체**(`.safetensors` 파일, "7B"의 그 숫자). 어텐션의 "attention weight(0.75)"와는 다른 개념이다. → [어텐션 §3.3](./260603-어텐션-기초.md)

## 2. ① 접근 방식 — open-weight vs closed

가장 큰 갈래이자 "오픈 웨이트 모델"이라는 말이 나오는 지점.

| 구분 | 뜻 | 예시 | 운영 |
|---|---|---|---|
| **Open-weight** (오픈 웨이트) | **모델 가중치 파일을 공개** → 다운받아 직접 실행 | Llama, Qwen, Mistral, DeepSeek, Gemma | **직접 서빙** (vLLM/SGLang on Runpod) — VRAM·KV 캐시 직접 관리 |
| **Closed / proprietary** | 가중치 비공개, **API로만** 사용 | GPT-4o, Claude, Gemini | API 호출만 — 서빙 인프라 불필요, prompt caching 등 API 기능만 활용 |

- **"open-weight ≠ 오픈소스"**: 오픈 웨이트는 *가중치 파일을 받을 수 있다*는 뜻이지, 훈련 데이터·코드까지 공개라는 뜻은 아니다. (라이선스도 제각각 — 상업적 사용 제한이 붙기도 함)
- **함의**: "모델을 직접 서빙한다"는 시나리오는 **open-weight일 때만** 성립한다. closed 모델은 가중치를 안 주므로 API 소비만 가능.
- 지금까지 공부한 어텐션·KV 캐시 지식은 전부 **오픈 웨이트 모델을 직접 돌릴 때** 쓰인다.

## 3. ② 훈련 단계 — base vs instruct

같은 모델이라도 두 버전이 올라와 있다.

| 종류 | 학습 내용 | 동작 | 용도 |
|---|---|---|---|
| **Base** (`Llama-3-8B`) | 다음 토큰 예측만 (pretraining) | 대화·지시 못 따름, 그냥 이어쓰기 | 파인튜닝 재료 |
| **Instruct / Chat** (`Llama-3-8B-Instruct`) | base + 지시 따르게 추가 학습(SFT/RLHF) | 질문에 답하고 지시 수행 | **챗봇·RAG·에이전트 = 거의 항상 이것** |

> ⚠️ 흔한 함정: base 버전을 서빙해놓고 "왜 대화가 안 되지?" 하는 경우. 서비스용은 **무조건 Instruct 버전**을 받아야 한다.

## 4. ③ 아키텍처 — Dense vs MoE

| 종류 | 뜻 | 예시 | 서빙 관점 |
|---|---|---|---|
| **Dense** | 모든 파라미터를 매 토큰마다 전부 사용 | Llama 8B/70B | 단순·예측 쉬움 |
| **MoE** (Mixture of Experts) | 전문가(expert) 여러 개 중 **일부만 활성화** | Mixtral 8x7B, DeepSeek-V3 | 총 가중치는 큼(**VRAM↑**) but 토큰당 실제 연산은 적음(**빠름**) — 독특한 트레이드오프 |

> MoE 메모: "8x7B"는 7B 전문가 8개라 가중치는 ~47B급 VRAM을 먹지만, 추론 시엔 보통 2개만 켜져 8B급 속도를 낸다. 큰 모델을 효율적으로 돌리려는 설계.

## 5. ④ 정밀도 변형 — 같은 가중치, 다른 포맷

같은 모델이 여러 버전으로 배포된다. **다른 모델이 아니라 같은 가중치의 압축·포맷 변형**이다. → [KV 캐시 §3.1 양자화](./260601-kv-cache-기초.md)와 같은 결.

```
Llama-3-8B-Instruct          ← FP16 원본       (~16GB VRAM)
Llama-3-8B-Instruct-AWQ      ← 4bit 양자화      (~5GB)   GPU 서빙용
Llama-3-8B-Instruct-GPTQ     ← 4bit 양자화      (~5GB)   GPU 서빙용
Llama-3-8B-Instruct-GGUF     ← CPU/로컬 포맷            llama.cpp용
```

- **FP16/BF16**: 원본 정밀도, 품질 최고, VRAM 최대
- **AWQ / GPTQ**: GPU 서빙용 4bit 양자화 (vLLM 등이 로드). 품질 약간↓, VRAM 대폭↓
- **GGUF**: llama.cpp 계열(CPU·로컬·Mac) 포맷
- VRAM 예산에 맞춰 고른다 (Runpod GPU 등급 ↔ 모델 크기·양자화 매칭)

## 6. 모델 고를 때 — 질문 순서

```
1. 가중치 받을 수 있나?  → open-weight(직접 서빙) vs closed(API)
2. 지시 따라야 하나?     → Instruct 버전 (서비스용은 거의 항상 yes)
3. 구조는?               → dense(무난) vs MoE(큰 모델 효율적으로)
4. VRAM에 맞나?          → 양자화 버전(AWQ/GPTQ/GGUF) 선택
```

## 7. VRAM 관점으로 한 번에 보기 (KV 캐시 연결)

직접 서빙(open-weight) 시 GPU VRAM은 두 곳에 쓰인다:

```
GPU VRAM
├── 모델 가중치   ← 고정 크기. 모델·양자화로 결정 (위 ④)
│                  대략: 파라미터 수 × 자료형 바이트
│                  예) 7B × FP16(2B) ≈ 14GB
└── KV 캐시       ← 가변 크기. 컨텍스트 길이·동시 요청에 비례
                   남은 VRAM = KV 캐시 풀 (vLLM --gpu-memory-utilization)
```

> 그래서 **큰 모델을 올릴수록 가중치가 VRAM을 많이 먹어 → KV 캐시 공간이 줄고 → 동시 처리량이 떨어진다.** 모델 종류·크기 선택이 곧 서빙 용량 산정과 직결된다. → 상세는 [KV 캐시 §3·§4](./260601-kv-cache-기초.md)
